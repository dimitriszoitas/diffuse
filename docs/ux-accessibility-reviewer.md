# UX & Accessibility Reviewer

Diffuse uses one combined Claude agent for screenshot reviews, with **99 original operational checks** informed by **96 public NN/g and W3C sources**. Sources were checked on **24 October 2026**. This is a versioned reference snapshot, not a live feed, a copied article archive, or an endorsed NN/g/W3C product.

## Use the reviewer

1. Open **Settings → AI** and keep your existing Anthropic API key.
2. Under **UX & accessibility review**, choose **UX & Accessibility Reviewer**.
3. Choose **Set up reviewer**. Diffuse creates one named agent in your Claude account and enables it after checking its configuration.
4. Open a page, start Diffuse and choose **Review with AI**. Add a focus or optional reference and run the review.
5. Inspect each suggestion, its highlighted area, its assessment and its source links. Accept only findings you want in the review.

The reviewer uses **Claude Opus 5.5, Max effort**, with a separate per-review spending limit (default $2). A final request already in progress may exceed that limit. It receives screenshots, instructions and any linked Figma context; Claude stores the session in your Anthropic account. It cannot navigate pages, run shell commands, browse the web, create tickets or change the reviewed app. Journey testing keeps its separate user and evaluator agents.

## What the labels mean

- **Visible observation:** supported by the captured screen; not proof of real-user difficulty or WCAG conformance.
- **UX recommendation:** an expert-review hypothesis grounded in the visible evidence and the referenced guidance.
- **Needs verification:** a potential concern that needs missing DOM, keyboard, assistive-technology, responsive or measurement evidence.

The library covers all 55 active WCAG 2.2 A/AA criteria, but this screenshot reviewer does **not** execute all those tests. It includes three explicitly labeled AAA enhancements and advisory ARIA patterns. No findings does not mean the page is accessible. It cannot measure human task time, success rate, SUS or SEQ from an AI run.

Each finding cites at most four relevant rules; the extension resolves their links from its local reference list. Imported reports treat those links as untrusted and only allow HTTPS NN/g or W3C URLs. Source links and assessment labels travel with accepted findings in HTML, Markdown and JSON review exports.

## Updating the reference

The canonical libraries are `extension/ux-knowledge.mjs` and `extension/accessibility-knowledge.mjs`. Recheck original pages, revise concise original checks and evidence requirements, update the library revision and date, and test thresholds and references. **Check reviewer** updates an existing agent in place when the packaged definition changes. New knowledge does not silently alter older review evidence.

## Review coverage

| Rule | Area | Check | Evidence needed |
| --- | --- | --- | --- |
| ux-language-match | mental-models | Check whether task labels, object names and action order match the intended audience’s concepts. Identify the specific internal term or unexpected relationship that obstructs a task. | Capture the label, its surrounding context, the stated audience and the observed destination or outcome. Treat an unfamiliar term as a hypothesis until its impact is observed. |
| ux-error-prevention | error-prevention | Before an action with significant consequences, check whether its scope is understandable and a proportionate safeguard or recovery path exists. Avoid recommending confirmation dialogs for every routine action. | Identify the affected records and visible consequence wording. Inspect existing confirmation or undo evidence without executing a destructive action merely to test it. |
| ux-help-in-context | help | When the task needs guidance, check whether concise help is available near the relevant decision and provides a usable next step. | Locate the confusing decision and available help. Quote only the application text needed to explain the problem; identify missing guidance as unverified if the help was not inspected. |
| ux-recognition | cognitive-load | Check whether users can see or retrieve earlier choices and relevant options when needed, rather than remembering hidden values, unexplained commands or prior screens. | Show the earlier information and the later decision that depends on it. Identify the unavailable cue and a visible alternative such as a summary, history or labelled option. |
| ux-persistent-form-labels | forms | Check that each field retains a clear visible label after entry, and that essential format instructions remain available while correcting the value. Placeholder text should not carry the only instruction. | Compare empty, focused and populated field states if available. A screenshot cannot establish the programmatic label; inspect semantic evidence separately. |
| ux-location-hierarchy | navigation | For deep hierarchical content, check whether users can identify their location and return to meaningful parent levels. Evaluate breadcrumbs as a supplement to navigation, and check their readability at the tested viewport. | Record the page hierarchy, visible path and link destinations. Do not demand breadcrumbs for a flat flow or mistake browsing history for hierarchy. |
| ux-information-scent | discoverability | Check whether a link’s wording and nearby context help the intended persona predict its destination and relevance to the goal. Flag misleading promises or ambiguous alternatives. | Compare the exact visible cue with the destination actually observed. Record unvisited alternatives as unknown instead of assuming that their content is missing. |
| ux-form-structure | forms | Check whether a long form groups related inputs, explains requirements before entry and makes its sequence understandable. Keep optional detail from obscuring the information needed to proceed. | Capture grouping, requirement text, dependencies and any repeated backtracking. Distinguish an observed obstacle from a preference for a different layout. |
| ux-table-finding | tables | Check whether records have understandable identifiers and whether search, filtering or sorting supports the stated task. Active filters and the scope of displayed results should be clear. | Inspect available search and filters plus relevant scrolling or pagination before asserting that a record cannot be found. Capture query, active filters and resulting rows. |
| ux-table-work | tables | Check whether comparison, record editing and bulk actions preserve enough row and column context. A user should understand which records an action affects and whether an edit is pending. | Capture headers, selected rows, edit state and action scope. Inspect only the table tasks relevant to this journey; do not mark untested modes as passing. |
| ux-progressive-disclosure | cognitive-load | Check whether common task controls stay discoverable while secondary detail can be revealed on demand. Disclosure labels should predict their contents; dependent information should remain easy to compare. | Record the initial choices, opened section and task dependency. Use actual task context to judge what is primary; avoid treating every hidden feature as a defect. |
| ux-exit-and-recovery | user-control | Check whether people can cancel, backtrack or reverse a mistaken choice without avoidable loss of entered work. Make the consequences of exiting a flow understandable. | Inspect the visible exit and any already recorded return or undo outcome. Do not claim preserved data or working recovery from the presence of a button alone. |
| ux-empty-states | system-feedback | Check whether a blank area distinguishes no existing content, no matching results, loading and failure, and offers a relevant next action where possible. | Capture the empty area after loading settles, active filters and the available next action. Do not infer a server failure from blank pixels alone. |
| ux-control-states | interaction-states | Check whether the observed enabled, unavailable, hover, focus, pressed, selected and loading states communicate what happened and what can happen next. Selected state must not be confused with a momentary press. | Use state-specific screenshots and execution or semantic evidence. List hover, keyboard focus and unavailable states as not tested unless actually exercised or directly inspected. |
| ux-error-recovery-copy | errors | Check whether a visible error identifies the affected input or operation, explains the problem in useful language and provides a plausible recovery action while preserving completed work. | Capture the triggering action, error placement and wording, retained values and any attempted correction. A generic message does not establish its underlying technical cause. |
| ux-validation-timing | errors | Check whether validation waits until input can reasonably be judged and whether requirements are available before submission. Reserve disruptive warning treatments for issues that warrant interruption. | Compare the initial, typing, blur and submit states that were actually observed. Report premature feedback only when its timing is evidenced. |
| ux-image-purpose | accessible-content | Check image alternatives in context: functional images need an understandable action name; informative images need an equivalent message; purely decorative images should not create redundant announcements. | Inspect the image’s role, accessible name or alt value and surrounding copy. Do not infer missing alternative text from a screenshot, or generate a description without understanding the image’s purpose. |
| ux-inclusive-scope | inclusion | Consider the access needs relevant to the stated audience and task, including visual, motor, auditory and cognitive barriers. Do not reduce accessibility to image descriptions or assume one persona represents everyone. | Name the specific barrier, affected interaction and observed evidence. Identify where testing with assistive technology or representative people is still needed. |
| ux-dialog-interruption | dialogs | Check whether an interrupting dialog is justified by the current task and whether it hides information needed to answer it. Prefer a less disruptive presentation when the task needs access to underlying context. | Record the triggering action, dialog contents, obscured reference information and dismissal path. Keep keyboard focus behavior separate unless it was tested. |
| ux-navigation-visibility | navigation | Check that the primary navigation is discoverable, communicates the current location and groups options meaningfully. Assess hiding choices against available space and the task’s need for orientation. | Inspect the initial menu state, expanded choices and current-location cue at the tested viewport. Do not generalize a mobile observation to desktop. |
| ux-system-feedback | system-feedback | After a meaningful action, check whether the interface confirms receipt, distinguishes work in progress from completion or failure, and communicates consequential state changes. | Use before/action/after evidence with timestamps where available. Separate application waiting from model or capture latency; do not call a task complete merely because the click succeeded. |
| ux-consistency | consistency | Check whether equivalent controls, terms and state treatments behave consistently across the observed product. Identify concrete surprises caused by conflicting meanings or departures from familiar conventions. | Provide both comparable instances and their outcomes. A single screen cannot establish a cross-product inconsistency, and intentional domain conventions may differ. |
| ux-scroll-discovery | discoverability | Check whether the initial viewport communicates the task’s purpose and indicates meaningful content below it. Inspect false endings or nested scroll areas that conceal necessary controls. | Capture the initial viewport and relevant content after scrolling. Absence from the first screenshot is not absence from the page; never conclude a flow is blocked without inspecting available scroll paths. |
| ux-icon-meaning | content | Check whether important icons communicate their action in this context and have useful visible labels where their meaning is ambiguous. Hover-only explanations do not serve touch interactions. | Record the icon, visible label, context and actual action. Semantic naming needs direct inspection; recognising the depicted object does not establish understanding of its function. |
| ux-interaction-effort | efficiency | Review avoidable reading, searching, typing, memory demands and context switches alongside clicks. Judge the effort required for the goal and audience rather than treating fewer actions as universally better. | Cite specific detours or repeated work. Keep automated action counts and model delays labelled separately from human task time; suggest a comparable route instead of inventing a human benchmark. |
| ux-mobile-continuity | mobile | At a narrow viewport, check whether important context and actions remain usable and whether interrupted work can be resumed. Avoid forcing users to memorise information across separate views. | Use the tested viewport, content visibility, actual input behavior and any observed return state. A desktop viewport resize alone does not prove real-device touch or keyboard behavior. |
| ux-clear-copy | content | Check task copy for unnecessary jargon, vague wording and buried instructions. Suggest a concise alternative that preserves the necessary meaning for the intended audience. | Identify the exact application phrase and the decision it obstructs. Consider specialist vocabulary that the stated audience may already understand. |
| ux-choice-differences | decision-making | Check whether similar choices explain their meaningful differences before commitment, especially consequences, scope and task-relevant tradeoffs. | Capture the available options and differentiating information. Explain which missing distinction could change the decision, without inventing undocumented features or prices. |
| ux-observation-scope | research-validity | Separate an expert-review hypothesis, an AI-simulated attempt and behavior observed from a real participant. Recommend representative-user testing for claims about comprehension or preference that inspection cannot establish. | State who or what performed the task, the goal, observed actions and any moderator guidance. Do not turn a simulated persona into a claim about a population. |
| ux-task-outcome | research-validity | Define completion from the requested result and verify the final state. Distinguish complete, partial and unverified outcomes; keep ordinal outcome labels separate from numeric rates. | List the required subgoals and evidence for each. Do not treat an attempted submission as success or infer a human success rate from an AI run. |
| ux-target-acquisition | input-effort | Inspect small, crowded or distant controls that make a common action difficult to acquire. Consider the actual activation area and nearby competing actions, rather than visual icon size alone. | Use measured target bounds or observed misactivation when available. A screenshot can suggest a risk but cannot prove a numeric accessibility failure or predict an individual’s movement time. |
| ux-rating-validity | research-validity | Keep expert ratings distinct from participant-reported usability or workload. SUS, SEQ and NASA-TLX require their own collection methods; do not manufacture these scores from a screenshot or automated journey. | State the rating method, source of responses and evidence scope. Mark missing participant data as unavailable, and avoid presenting custom agent scores as validated research instruments. |
| ux-icon-evidence | research-validity | Separate whether an icon’s shape is recognisable, whether its action is understood and whether people can find or activate it. Match each claim to the corresponding observation. | Capture the task context and any actual interpretation or activation result. Treat a proposed label improvement as a recommendation until validated with relevant users. |
| a11y-audit-scope | scope | Report a scoped accessibility review, not automatic conformance certification. Keep confirmed findings, possible concerns, not-applicable checks and unverified checks distinct; an empty finding list is not a pass. | State the pages, states, methods and evidence actually inspected. Screenshot plus limited visible DOM does not test keyboard, screen readers, computed contrast or the entire site. Request manual verification for unsupported checks. |
| a11y-aria-support | semantics | APG patterns are implementation guidance, not additional WCAG success criteria. ARIA changes semantics but does not supply keyboard behavior; prefer native elements and test actual browser/assistive-technology combinations. | Require markup plus working interaction tests; record tested combinations and remaining gaps. An APG resemblance or added role cannot certify accessibility. |
| a11y-modal-dialog | dialogs | A modal needs meaningful labeling, appropriate initial focus, contained keyboard traversal, an accessible close route and sensible focus return; background interaction should be inert. | Open and close the actual dialog using keyboard; record initial focus, traversal, escape/close, return destination and semantics. Visual dimming alone does not prove modality. |
| a11y-combobox | widgets | Match combobox semantics and keyboard behavior to its editable/select-only and popup type; expose the name, expanded state, active/selected option and relationships. | Inspect actual properties and test opening, option navigation, selection, dismissal and text editing where applicable. A dropdown screenshot does not identify its interaction model. |
| a11y-tabs | widgets | Associate tabs with panels, expose selection and support appropriate tab/arrow/activation keys. Automatic activation should not introduce noticeable panel-loading delay. | Test traversal, manual or automatic activation and panel access with keyboard; inspect tablist/tab/tabpanel relationships. Static selected styling is insufficient. |
| a11y-accordion | widgets | Use named expandable controls with appropriate heading structure and accurate expanded/panel relationships; support keyboard activation and access to revealed content. | Test expansion/collapse and keyboard traversal; compare actual expanded properties with visible panels. Do not treat optional arrow-key behavior as mandatory. |
| a11y-menu-button | widgets | For an actual menu button, expose popup and expanded state and move focus into the menu on activation. Ordinary site navigation need not adopt application-menu semantics. | Test Enter/Space activation and focus placement; inspect button and menu properties. Do not infer menu role solely from a chevron or dropdown appearance. |
| a11y-listbox | widgets | Expose options and selection with the intended single/multiple-selection interaction. Listbox options should not contain independently interactive buttons or links; use a suitable alternative pattern. | Inspect option semantics and test keyboard focus versus selection, scrolling and activation. A visible selected row does not establish screen-reader operation. |
| a11y-1-1-1 | 1.1.1 (A) | Give meaningful images and controls an equivalent text alternative; hide purely decorative content from assistive technology. Apply the criterion-specific media, test, sensory and CAPTCHA exceptions. | Inspect actual accessible names or alternatives and compare with the content purpose.
